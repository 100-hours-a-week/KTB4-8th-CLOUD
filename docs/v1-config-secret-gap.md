# 앱 코드와 Secret 값이 어긋날 때의 위험과 대응

2026-09-30 [SENTRY_DSN 롤백 사례](troubleshooting/2026-09-30-ai-sentry-dsn-rollback.md)를 계기로 정리했다. 앱 코드가 기대하는 환경변수와 운영 Secret 값이 **어긋난 시간**(키가 없거나, 임시 값이거나, 형식이 틀린 시간)이 생길 때 운영에 무슨 일이 생기는지, 어떻게 막는지, 각 방법의 대가는 무엇인지 적는다.

## 한 줄 요약

**대부분은 서비스가 멈추지 않는다.** 배포 전에 멈추거나, 새 버전이 실패하면 이전 버전으로 돌아가기 때문이다. 하지만 **세 가지 경우는 실제 장애나 "조용한 고장"이 된다.** 새 버전이 알림 없이 반영되지 않는 경우, Secret만 바꾼 배포가 롤백까지 실패하는 경우, 앱은 뜨는데 기능만 고장 나는 경우다. 싸고 효과 큰 순서는 ① 롤백·차단 알림 ② Secret 형식 검사 ③ 선택 기능은 앱이 설정 오류를 견디게 하기 ④ 새 환경변수 도입 순서 합의다.

## 먼저 알아야 할 우리 구조의 동작

| 사실 | 의미 |
| --- | --- |
| Secret은 **배포할 때만** 컨테이너에 들어간다 | Secrets Manager 값을 바꿔도 돌고 있는 컨테이너는 그대로다. Docker가 컨테이너를 자동 재시작해도 만들 때의 값을 쓴다 |
| 배포는 매번 BE·AI Secret을 **모두** 조회한다 | FE만 바뀐 배포도 AI Secret을 읽는다. Secret 파일 내용이 바뀌었으면 **그 배포에서 해당 서비스를 재생성한다** |
| 필수 키가 없거나 형식이 틀리면 **배포 전체가 멈춘다** (`runtime_prepare_failed`) | 컨테이너는 하나도 안 바뀐다. 대신 FE·BE 등 **다른 서비스 배포까지 같이 막힌다.** Discord 알림은 간다 |
| 선택 키가 없으면 경고만 남기고 넘어간다 | 앱은 그 기능 없이 뜬다. 알림은 없다 |
| 새 버전이 health 검증에 실패하면 **이미지만** 이전 버전으로 되돌린다 | **Secret 값은 되돌리지 않는다.** 롤백된 옛 이미지도 최신(잘못된) Secret으로 뜬다 |
| 롤백에 성공하면 알림을 보내지 않는다(TD-013) | 새 버전이 차단돼도 결과는 `rolled_back`이나 `unchanged`로만 남는다 |

관련 결정: [TD-013](technical-decisions.md#td-013--장애-알림-자동-복구되지-않은-경우만-discord), [TD-016](technical-decisions.md#td-016--배포-시-secret-자동-조회와-실패-처리), [TD-019](technical-decisions.md#td-019--ai-secret-키-전달-범위와-sentry_dsn)

## 어긋남이 생기는 방식과 운영 영향

| # | 상황 | 무슨 일이 생기나 | 서비스 영향 | 알림 |
| --- | --- | --- | --- | --- |
| 1 | **필수 키**가 없음·형식 틀림 | 배포 전에 멈춤 | 없음. 단 **모든 서비스의 배포가 막힘** | 있음 |
| 2 | **선택 키**가 없음 (예: SENTRY_DSN 미입력) | 앱이 그 기능 없이 뜸 | 기능 조용히 꺼짐 (에러 수집·추적 안 됨) | 없음 (로그 경고만) |
| 3 | 키가 **먼저** 들어가 있고 쓰는 코드는 아직 없음 | 아무 일 없음 | 없음. 단 **임시·예시 값이면 코드가 배포되는 순간 3~5번이 됨** | — |
| 4 | **새 이미지** + 잘못된 값 → 앱이 시작 시 죽음 (이번 사례) | 새 버전 실패 → 이전 이미지로 롤백 → 차단 | 없음 (이전 버전 유지). 대신 **새 버전·설정 변경이 반영 안 됨** | **없음** |
| 5 | **Secret만 변경** + 잘못된 값 → 앱이 시작 시 죽음 | 같은 이미지로 재생성 실패 → 롤백도 **같은 이미지 + 같은 잘못된 값**이라 실패 | **해당 서비스 장애** (`rollback_failed`) | 있음 |
| 6 | 값이 형식은 맞지만 **실제로는 무효** (만료·폐기된 API 키, 잘못된 비밀번호) → 앱은 뜸 | health 통과 → 배포 성공 | **기능 장애** (해당 요청 실패). 롤백 안 됨 | 없음 |
| 7 | 이전 버전 코드도 그 값을 쓰는데 값이 틀림 | 4번에서 롤백한 옛 이미지도 죽음 | **해당 서비스 장애** (`rollback_failed`) | 있음 |

이번 SENTRY_DSN 사례는 **4번**이었다. 옛 AI(`f7476b5`)가 Sentry를 쓰지 않았기 때문에 롤백이 성공해 장애가 없었다. 옛 버전도 Sentry를 썼다면 **7번(장애)**이 됐다.

"Secret은 배포할 때만 반영된다"는 특성 때문에 **Secret을 바꾼 사람과 그 값이 적용되는 시점이 분리된다.** AI Secret을 고쳐 두면, 다음에 FE 파트가 병합해 자동 배포가 도는 순간 AI도 재생성되며 새 값이 적용된다. 값이 틀렸다면 **FE 배포 때 AI가 죽는 5번**이 된다.

## 해결 방법과 트레이드오프

| 방법 | 막는 상황 | 장점 | 대가·한계 | 담당 |
| --- | --- | --- | --- | --- |
| **A. 롤백·차단 알림** — `rolled_back`, 차단으로 건너뜀(`blocked`)을 Discord로 알림 | 4번이 묻히는 것 | 코드 몇 줄. 어떤 원인이든 "새 버전이 안 나갔다"를 바로 앎 | 알림이 늘어남. 원인은 로그를 봐야 함 | Cloud (TODO 등록) |
| **B. Secret 형식 검사** — prepare-runtime.py가 키별 형식(DSN, URL, PEM 등)을 검사 | 1·3·4·5·7번 중 **형식 오류** | 배포 전에 걸러 서비스를 안 건드림 | 키마다 규칙을 관리해야 함. **6번(형식은 맞는데 무효)은 못 막음.** 선택 키를 "틀리면 전달 안 함"으로 하면 기능이 조용히 꺼짐(2번과 같아짐) | Cloud (SENTRY_DSN TODO 등록) |
| **C. 앱이 선택 기능 설정 오류를 견딤** — 예: Sentry 초기화 실패 시 경고 로그만 남기고 계속 기동 | 선택 기능(에러 수집·추적·분석)의 4·5·7번 | 부가 기능 때문에 본 서비스가 죽지 않음 | 해당 파트 코드 수정. 실패가 조용해지므로 로그·지표로 드러내야 함. **필수 기능(DB·LLM 키)에는 쓰면 안 됨** (틀린 채로 떠서 6번이 됨) | 각 앱 파트 |
| **D. 새 환경변수 도입 순서 합의** — 값 입력 → 형식 확인 → Cloud 전달 시작 → 코드 배포 | 3번(임시 값)이 4번으로 번지는 것 | 비용 없음. 파트 간 "누가 언제" 명확 | 사람이 지켜야 함. 급할 때 건너뛰기 쉬움 | 파트 간 합의 |
| **E. 롤백할 때 Secret도 되돌림** — 마지막 정상 배포의 env 파일을 보관했다가 이미지와 함께 복원 | 5·7번 | 잘못된 값으로 인한 장애를 자동 복구 | 구현이 커짐. **이미 폐기·교체된 비밀번호·키로 되돌릴 수 있음**(DB 비밀번호를 바꾼 경우 옛 값은 더 이상 안 통함). 보관 파일도 비밀이라 관리 대상 증가 | Cloud |
| **F. 배포 후 기능 확인(smoke test)** — 실제 API 한두 개를 호출해 결과 확인 | 6번 | 형식이 아니라 **실제 동작**을 확인 | 배포 시간 증가. LLM 호출 비용·부작용. 시험용 요청·계정 설계 필요 | Cloud + 앱 파트 |
| **G. Secret 조회를 서비스별로 분리** — AI Secret이 틀려도 FE·BE 배포는 진행 | 1번의 "다른 서비스 배포까지 막힘" | 한 파트의 실수가 다른 파트 배포를 막지 않음 | 로직이 복잡해짐. "AI만 옛 설정으로 남은 상태"를 알림으로 드러내야 함 | Cloud |
| **H. 스테이징 환경** — 운영과 같은 구성에 먼저 배포 | 거의 전부 | 운영 전에 코드·설정 조합을 실제로 확인 | 서버·DB 비용과 관리 부담이 두 배 가까이 됨. V1 단일 EC2 규모에는 과함 | V2 설계 |

## 추천 순서

1. **A. 롤백·차단 알림** — 가장 싸고, 어떤 원인이든 "조용히 안 나간 배포"를 없앤다. 이번 사례에서 1시간 반을 모르고 지나간 것이 이것 때문이다.
2. **B. SENTRY_DSN 형식 검사** — 이미 겪은 오류라 규칙이 명확하다. 앞으로 새 키를 추가할 때 같은 방식으로 규칙을 붙인다.
3. **D. 도입 순서 합의** — 비용 없이 바로 할 수 있다. 아래 절차를 파트 간에 공유한다.
4. **C. 선택 기능의 설정 오류 견디기** — AI 파트와 BE 파트에 요청한다. Sentry·LangSmith처럼 없어도 서비스가 도는 기능만 대상이다.
5. **E·F·G·H** — 사고가 반복되거나 규모가 커질 때 검토한다. E는 비밀번호 교체와 충돌하는 점, H는 비용을 먼저 따진다.

## 새 환경변수를 추가할 때의 절차 (D)

앱 파트가 새 Secret 기반 환경변수를 쓰는 코드를 만들 때:

1. **앱 파트:** 키 이름, 필수/선택 여부, 올바른 값 형식, 없을 때 앱의 동작을 Cloud에 알린다. 선택 기능이면 값이 없거나 틀려도 기동하게 만든다(C).
2. **앱 파트:** Secrets Manager에 **실제로 쓸 값**을 넣는다. 임시·예시 값을 넣어 두지 않는다. 아직 값이 없으면 키를 만들지 않는다.
3. **Cloud:** 운영 값의 형식을 확인한다. 값은 출력하지 않고, 예를 들어 `grep -cE '<형식>' ai.env`로 본다. 확인 후 prepare-runtime.py 전달 목록에 추가하고, 가능하면 형식 검사(B)도 함께 넣는다.
4. **Cloud:** 전달 목록 변경을 main에 반영한다. 이 배포에서 해당 서비스가 재생성되며 값이 들어간다. 이때 옛 코드는 새 값을 쓰지 않으므로 안전한지 확인한다.
5. **앱 파트:** 그다음에 새 값을 쓰는 코드를 main에 병합한다. 자동 배포 후 기능과 Sentry 등 연동이 실제로 동작하는지 확인한다.

**Secret 값을 바꿀 때:** 바꾼 사람이 곧바로 Deploy production을 수동 실행하고 결과를 확인한다([운영 절차](v1-operations.md) 8절). 다른 파트의 자동 배포에 "얹혀서" 적용되지 않게 한다.
