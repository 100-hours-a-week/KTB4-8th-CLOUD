# KeepGo V2 — 컨테이너 기반 서비스 확장 및 운영 자동화 설계

# 1. V1 기준 문제 정의

## 1.1 상황

```
서비스가 빠르게 성장했습니다.
트래픽은 성장했지만 이를 대비할 팀원의 수는 크게 증가하지 않았습니다.

초기에는 하나의 EC2와 Docker Compose로 서비스를 빠르게 출시하는 것이
가장 중요한 목표였습니다.
하지만 사용자와 트래픽이 증가하면서 단일 EC2가
서비스의 확장성과 가용성을 제한하기 시작했습니다.
```

KeepGo는 초기 시장 검증을 마치고 성장 단계에 진입했다. MVP 단계의 MAU 140명, 0.14 RPS에서 **MAU 80만 규모**로 성장한 상황을 가정한다.

조직 규모와 비용 여력은 그대로이므로, 가용성과 확장성을 확보하되 **운영 인력을 늘리지 않고 자동화로 해결**하는 것이 이번 단계의 제약 조건이다.

## 1.3 워크로드 특성

KeepGo의 부하는 단순 HTTP 요청량으로 판단할 수 없다. **YouTube Sync 한 건이 여러 개의 AI 분석 Job으로 증폭**되기 때문이다.

```
Sync 요청 증가
    ↓
AI 분석 Job 증가
    ↓
Worker CPU·Memory 사용 증가
    ↓
Backend / AI API와 자원 경합
    ↓
사용자 요청 처리 성능 저하
```

Backend와 Worker는 부하를 판단하는 기준 자체가 다르다.

| 구분 | 부하 지표 |
| --- | --- |
| Backend | RPS, CPU, Memory, p95 응답시간, DB Connection |
| Worker | Queue Depth, Job 처리량, 가장 오래된 Job 대기시간 |
| SSE | 동시 연결 수, 이벤트 전송량, 메모리 |

## 1.4 한계 6가지

### ① Workload별 독립적인 Capacity 조절 불가

Backend, AI API, Worker가 하나의 EC2 자원을 공유한다.

- 평상시 부하 기준으로 구성하면 피크 시간대에 처리 지연 발생
- 피크 부하 기준으로 상시 유지하면 평상시 자원 낭비
- AI 분석량만 증가해도 전체 EC2를 Scale-Up해야 함

### ② SQL이 서비스 DB와 Job Queue 역할을 동시에 수행

현재 DB는 서비스 데이터 저장과 AI 분석 작업 상태 관리를 함께 담당한다.

| 서비스 DB 역할 | Job Queue 역할 |
| --- | --- |
| 사용자·인증 데이터 | PENDING 작업 조회 |
| YouTube 콘텐츠 | 작업 선점 |
| 장소·이벤트 | RUNNING 상태 갱신 |
| 챗봇 대화 상태 | 재시도 횟수 관리 |
| 추천 결과 | SUCCESS·FAILED 처리 |

> 처리 지연을 허용할 수 있는 백그라운드 작업이, 즉시 응답해야 하는 사용자 API의 DB 자원까지 소모한다.

**이 가설은 실측으로 검증했다.** 2 vCPU / 1 GiB로 제한한 MySQL에서 사용자 API 부하를 고정한 채 Worker 동시성만 늘린 결과, **API p95 지연이 10~29배 악화**되었고 Worker 자신의 처리량도 절반 이하로 떨어졌다.

[🔗 실험 문서 링크](https://app.notion.com/p/sysbench-3dfed9d9a307801789bbdbce38c7c233?source=copy_link)

### ③ 다중 Instance 운영 및 배포 자동화 한계

Scale-Out으로 인스턴스가 늘어나면 다음 작업이 함께 증가한다.

- 여러 Instance에 동일한 Application Version 배포
- 신규 Instance 환경 구성
- 장애 Instance 탐지 및 제외·교체

서비스 규모는 빠르게 증가했지만 운영 인력은 늘지 않았다. 수동 대응이 불가능하다.

### ④ 단일 Public EC2 중심의 네트워크 구조

```
Internet → 80/443 → Public EC2 (Nginx, Backend, AI API, Worker) → Private RDS
```

하나의 EC2가 외부 트래픽 수신, TLS 종료, 정적 파일 제공, API 프록시, 애플리케이션 실행, 외부 API 통신, DB 접근을 모두 담당한다.

- **가용성**: ALB가 없어 EC2 장애 시 트래픽을 다른 인스턴스로 전환할 수 없다
- **보안**: 공개 서버가 침해되면 같은 호스트의 애플리케이션과 IAM Role, RDS 접근 경로까지 영향을 받는다

### ⑤ 실시간 알림 증가에 대한 Backend 확장 한계

KeepGo는 팝업·전시처럼 기간이 존재하는 이벤트를 다루며, 시작 D-7·D-1과 종료 D-2 시점에 알림을 제공한다. 서비스가 성장하면 Backend가 유지해야 하는 실시간 Connection 수도 함께 증가한다.

- 장기 Connection을 여러 Backend에 어떻게 분산·유지할 것인가
- 배포 및 인스턴스 교체 시 Connection 종료와 Client 재연결

### ⑥ Recreate 배포에 따른 서비스 중단 영향 증가

무중단이 반드시 필요한 서비스는 아니지만, 사용자가 늘고 인스턴스가 여러 대가 되면 롤링 배포를 적용하기 쉬워지므로 굳이 중단시킬 이유가 줄어든다.

# 2. 개선 방향 요약

> 사용자 요청과 AI 분석 Workload가 동시에 증가하고 있으며, 부하 특성이 다른 Backend와 Worker를 하나의 EC2에서 함께 운영하기 어려워졌다. 또한 서버 수가 증가하면 제한된 운영 인력으로 수동 배포와 장애 대응을 지속하기 어렵다.

## 2.1 이번 단계에서 해결할 것

| # | 문제 | V2 해결 방향 |
| --- | --- | --- |
| ① | Workload 독립 확장 불가 | Backend / AI API / SSE / Worker를 **별도 ECS Service로 분리**하고 각각 확장 |
| ② | DB가 큐 역할 겸용 | **SQS**로 작업 전달 분리, MySQL은 작업 원장만 유지 |
| ③ | 배포·운영 수동 대응 | **ECS + ASG**로 배포·교체·복구 자동화 |
| ④ | 단일 진입점 | **ALB** 도입, 애플리케이션을 Private Subnet으로 이동 |
| ⑤ | 실시간 연결 확장 한계 | **SSE 서버 분리**, Redis Pub/Sub로 이벤트 전달 |
| ⑥ | 배포 중단 | ECS **롤링 배포** |

## 2.2 전략 선택: Scale-Up이 아닌 Scale-Out

| 방식 | 장점 | KeepGo에 부적합한 이유 |
| --- | --- | --- |
| Scale-Up | 구조 변경 없음, 단순 | Backend·Worker를 독립 확장 못 함. 이벤트 Peak 기준으로 상시 유지하면 평시 자원 낭비 |
| **Scale-Out** | 필요한 만큼만 확장, 장애 영향 범위 축소, 배포 중 서비스 유지 | 운영 복잡도 증가 → **자동화로 상쇄** |

트래픽이 평시 107 RPS에서 이벤트 853 RPS로 **8배 변동**하므로, 고정 Capacity 방식은 비효율적이다.

## 2.3 우리가 답한 세 가지 질문

**Q1. 우리 트래픽의 성격은?**

예측 불가능한 순간 피크 + 증폭되는 백그라운드 작업 → **Auto Scaling + Queue**

**Q2. 무엇을 내줄 수 있나?**

빠른 배포보다 **안전한 배포**. 비용은 여전히 중요하지만, 성장에 맞춘 가용성과 확장성에 우선순위를 둔다.

**Q3. 우리가 운영할 수 있나?**

- 기존 Docker Image 유지
- Backend / AI API / SSE / Worker를 Service 단위로 분리 (EC2는 공유)
- ALB Health Check로 비정상 인스턴스 자동 제외
- 알려진 행사에는 사전 확장
- 불변 Image Tag와 자동 Rollback

# 3. 구성요소별 선택과 사이징

## 3.1 컨테이너 오케스트레이션 — ECS on EC2

### 선택

**Amazon ECS + EC2 Launch Type (ASG Capacity Provider)**

### ECS 구성 개념

| 구성요소 | 역할 |
| --- | --- |
| Cluster | 컨테이너를 실행할 전체 공간 |
| Task Definition | 컨테이너 실행 설계도 (이미지, CPU/메모리, 환경변수) |
| Task | 실제 실행된 컨테이너 묶음 |
| Service | Task를 원하는 개수만큼 계속 유지 |

### 근거

KeepGo의 트래픽은 **이벤트 발생 시 버스트**가 핵심 성격이다. 초기에는 서버리스도 검토했으나, MAU 80만 환경에서 안정적으로 가용성을 확보하면서 비용과 인스턴스 관리를 통제하기 위해 ECS를 선택했다.

**Fargate가 아닌 EC2를 선택한 이유**

| 항목 | Fargate | ECS on EC2 |
| --- | --- | --- |
| 비용 | vCPU·메모리 단가가 높음 | EC2 온디맨드/Savings Plan 적용 가능 |
| 인스턴스 제어 | 불가 | 인스턴스 타입·크기 직접 선택 |
| 컨테이너 밀도 | Task당 독립 | 한 인스턴스에 여러 Task 배치 가능 |
| 운영 부담 | 낮음 | AMI·ASG 관리 필요 |

평시 1대 수준의 소규모 운영에서는 **EC2 쪽이 비용 효율이 높고**, 인스턴스 타입을 워크로드별로 고를 수 있다는 점이 Backend·SSE·Worker의 특성이 서로 다른 KeepGo에 유리하다.

### 서비스 분리

| ECS Service | 실행 내용 | 확장 기준 |
| --- | --- | --- |
| `keepgo-backend` | Spring Boot Backend | ALB 요청 수, CPU |
| `keepgo-ai-api` | 온라인 AI API (FastAPI) | 동시 처리 요청 수, 외부 API 지연 |
| `keepgo-sse` | SSE 스트리밍 서버 | 동시 연결 수, 메모리 |
| `keepgo-worker` | 동기화·영상 분석 Worker | SQS 적체량, 가장 오래된 메시지 나이 |

### 온라인 AI API를 별도 Service로 두는 이유

V1의 문제는 Backend·AI API·Worker가 **자원 상한 없이 한 호스트를 공유**한 것이었다. V2에서는 네 구성요소를 각각 별도 Service로 정의하고 **Task 단위로 CPU·메모리를 예약**해 자원 경계를 만든다.

특히 Backend와 온라인 AI는 부하 특성이 다르다.

| 구분 | Backend | 온라인 AI API |
| --- | --- | --- |
| 요청당 처리 시간 | 수십 ms | Gemini 응답까지 수 초 |
| 자원 점유 방식 | 짧게 쓰고 반환 | 스레드·커넥션을 길게 점유 |
| 확장 기준 | RPS | 동시 처리 요청 수 |
| 배포 주기 | 백엔드 담당 | AI 담당 (프롬프트·모델 변경) |

같은 Task에 두면 대기가 긴 AI 호출이 짧은 API 요청을 막고, AI 프롬프트만 수정해도 Backend까지 재배포해야 한다.

**추가 비용 없이 분리할 수 있다.** ECS에서 Service를 나눠도 EC2가 늘어나는 것이 아니라, 같은 Capacity Provider의 인스턴스에 Task가 배치된다.

```
Capacity Provider (ASG, EC2 공유)
 ├─ keepgo-backend
 ├─ keepgo-ai-api
 ├─ keepgo-sse
 └─ keepgo-worker
```

각 Service의 Task 수가 늘어 인스턴스 자원이 부족해지면 그때 Capacity Provider가 EC2를 추가한다.

> **온라인 AI와 백그라운드 분석이 같은 실행 환경을 공유하지 않는 것**을 우선 원칙으로 한다. 온라인 AI는 `keepgo-ai-api`, 백그라운드 분석은 `keepgo-worker`에서 실행한다.

Service 간 내부 통신은 ECS Service Connect 또는 Service Discovery를 사용하며, AI API는 **ALB에 노출하지 않는다.**

## 3.2 Auto Scaling 전략

### 계층별 확장

```
ECS Service Auto Scaling (Task 수 조절)
            ↓
ASG Capacity Provider (EC2 수 조절)
```

Task를 늘릴 자리가 부족하면 Capacity Provider가 EC2를 추가한다.

### 서비스별 확장 지표

| 서비스 | 주 지표 | 보조 지표 |
| --- | --- | --- |
| Backend | `ALBRequestCountPerTarget` | CPU, p95 응답시간, DB Connection 대기 |
| AI API | 동시 처리 요청 수 (커스텀 지표) | 외부 API 지연·429, CPU, 메모리 |
| SSE | 동시 연결 수 (커스텀 지표) | 메모리, 네트워크 처리량 |
| Worker | `ApproximateNumberOfMessagesVisible` ÷ Task 수 | 가장 오래된 메시지 나이, 외부 API 429 |

> AI API는 외부 응답 대기가 길어 **CPU 사용률이 낮은 상태에서도 포화**될 수 있다. 처리 중인 요청 수를 주 지표로 사용한다.

> SSE는 대부분의 연결이 Idle이므로 **CPU만으로 확장 여부를 판단할 수 없다.** Worker는 큐의 전체 길이가 아니라 **인스턴스당 적체량**을 기준으로 한다.

### 확장 지연을 고려한 정책

| 항목 | 기본값 | 대응 |
| --- | --- | --- |
| ASG 쿨다운 | 300초 | 예정된 이벤트에는 **사전 확장(Scheduled Scaling)** |
| 인스턴스 워밍업 | 300초 | EC2 기동 + 컨테이너 시작 + 애플리케이션 초기화 시간 확보 |
| ALB Health Check | 30초 간격, healthy 5회 | 신규 인스턴스가 트래픽을 받기까지 2~3분 소요 |

**순간 집중계수 2배의 버스트는 초 단위로 들어오지만 확장은 분 단위다.** 따라서 평시에도 최소 용량을 0으로 두지 않고, 알려진 이벤트 전에는 사전 확장한다.

## 3.3 Backend 애플리케이션 서버

### 역할

- 일반 API 요청 처리, 인증·인가
- 사용자 및 대화 상태 관리
- 데이터 조회·저장, 추천 조건 필터링
- 온라인 AI 호출 및 결과 처리
- Sync 작업 접수와 Outbox 기록

### 인스턴스 사이징

**초기 기준: `c7i.large` (2 vCPU / 4 GiB)**

| 후보 | 사양 | 서울 단가 | 판단 |
| --- | --- | --- | --- |
| `m7i.large` | 2 vCPU / 8 GiB | $0.1239 | 8 GiB가 필요하다는 근거 부족 |
| **`c7i.large`** | 2 vCPU / 4 GiB | **$0.1008** | CPU 크레딧 비의존, 메모리 적정 |
| `t3.medium` | 2 vCPU / 4 GiB | $0.052 | 버스터블. 주말 수백 RPS 지속 시 크레딧 의존 위험 |

Backend는 API 처리·DB 접근·외부 API 호출로 **CPU와 네트워크 사용이 지속되는 워크로드**다. 주말·저녁에 수백 RPS가 일정 시간 지속될 가능성이 있어 CPU 크레딧에 의존하지 않는 C 계열을 선택했다.

### 참고 벤치마크

공개된 Spring PetClinic 벤치마크(Spring Boot 4.0.3 + JPA, `c7i.large`, RDS `db.t3.micro`, 컨테이너 1 CPU / 512 MB 제한)에서 조회·저장 혼합 부하 50 VU로 10분간 측정한 결과는 다음과 같다.

| 항목 | 결과 |
| --- | --- |
| 처리량 | 434 RPS |
| p50 | 8 ms |
| p95 | 64 ms |
| p99 | 110 ms |
| Error | 0 |

> **이 수치를 KeepGo의 인스턴스당 처리량으로 직접 적용하지 않는다.** DB 엔진, 쿼리 구조, 비즈니스 로직이 다르다. 제한된 자원의 Spring Boot가 DB 접근을 포함한 혼합 요청에서 수백 RPS를 처리한 사례라는 점만 초기 기준 선정의 참고로 활용한다.

### 필요 인스턴스 수 산정

```
필요 인스턴스 수 = 올림(목표 RPS ÷ 인스턴스당 안정 처리 RPS)
```

인스턴스당 안정 처리 RPS는 구현 후 부하 테스트로 확정한다. 측정 시 정상 Peak뿐 아니라 **1.5배·2배**까지 부하를 올려 확인한다.

### Scale-Out 시 함께 확인할 것

- RDS 최대 Connection 수
- 외부 AI·지도 API Rate Limit
- 인스턴스 기동 및 애플리케이션 초기화 시간
- 인스턴스 간 세션·상태 공유 여부 (**Stateless 유지**)

## 3.4 SSE 스트리밍 서버

### 역할

- 챗봇 응답 스트리밍
- 추천 진행 상태 및 결과 전달
- 영상 분석 진행률·완료 알림
- 접속 중 In-App 알림

### Backend와 분리하는 이유

| Backend | SSE |
| --- | --- |
| 짧은 Request/Response | 장시간 Connection 유지 |
| RPS 기준 확장 | 동시 연결 수 기준 확장 |
| 배포 시 요청 재시도로 흡수 | 배포 시 Connection 전체 종료 |

함께 운영하면 SSE 연결 증가만으로 Backend 전체를 Scale-Out해야 하고, Backend 배포가 Streaming Connection을 끊는다.

### 인스턴스 사이징

**초기 기준: `t3.medium` (2 vCPU / 4 GiB)**

SSE는 CPU 연산보다 **Connection 유지와 네트워크 I/O 비중이 큰** 워크로드이며, 알림용 연결은 대부분 대기 상태다. 낮은 비용으로 실제 Connection 처리량을 먼저 확인하는 것이 목적이다.

> **검토 제안**: `t4g.medium`(서울 $0.0416)은 같은 2 vCPU / 4 GiB에 **20% 저렴**하고, t3가 2 vCPU를 1개 물리 코어의 스레드로 제공하는 것과 달리 **2개 물리 코어**를 제공한다. Graviton 이미지 빌드가 가능하다면 t4g 전환을 검토한다.

### 참고 벤치마크

| 출처 | 조건 | 결과 |
| --- | --- | --- |
| WSO2 Streaming API | 동시 5,000 Connection, 연결당 10 events/sec, 평균 82 Bytes | Error 0% |
| Spring WebPerf | 1 요청당 100 messages × 200 chars, 16 Thread | MVC+Tomcat 1,933 ops/s, WebFlux+Netty 4,614 ops/s |

> WSO2는 API Gateway 환경이므로 5,000 Connection을 인스턴스당 Capacity로 직접 적용하지 않는다. **초기 부하 테스트 범위를 설정하는 참고 자료**로만 사용한다.

### Scale-Out 시 고려사항

| 항목 | 내용 |
| --- | --- |
| 기존 연결 재분배 | Scale-Out해도 기존 Connection은 이동하지 않는다. **피크 전 선제 확장 필요** |
| ALB Idle Timeout | 기본 60초. SSE Heartbeat를 더 짧은 주기로 전송하거나 Timeout 조정 (1~4,000초 설정 가능) |
| Deregistration Delay | 기본 300초. 배포·Scale-In 시 기존 연결 정리 시간 확보 |
| Client 재연결 | backoff + jitter 적용, 재접속 후 누락 알림 재조회 |

### 이벤트 전달 — Redis Pub/Sub

```
Backend 또는 Worker → Redis 채널 → 해당 채널 구독 SSE 서버 → 사용자 연결
```

사용자·요청 단위로 채널을 구분하고, 인증·인가로 타인 채널 구독을 차단한다.

> Redis Pub/Sub는 구독자가 놓친 이벤트를 보존하지 않는다. **알림 기록과 Job 최종 상태는 MySQL에 남긴다.**

## 3.5 데이터베이스 — RDS MySQL

### 선택

- MySQL은 트랜잭션과 관계 무결성이 필요한 서비스 데이터에 적합하다
- 개발자·ORM·운영 도구 생태계가 풍부하다
- RDS에서 데이터 모델을 유지한 채 인스턴스 사양과 스토리지를 단계적으로 확장할 수 있다

### 사이징 결론

| 단계 | 클래스 | 사양 | 스토리지 |
| --- | --- | --- | --- |
| V1 | `db.t4g.micro` | 2 vCPU / 1 GiB | gp3 20 GB |
| **V2** | **`db.t4g.small`** | **2 vCPU / 2 GiB** | gp3 100 GB |

**상향 근거 요약**

| 축 | micro | small | 효과 |
| --- | --- | --- | --- |
| 버퍼 풀 | 약 0.6 GiB | 약 1.2 GiB | 데이터를 메모리에 유지. 실측상 버퍼 풀을 벗어나면 처리량 5.5배·지연 29배 악화 |
| 커넥션 상한 | 80 미만 | 약 160 | Backend 스케일아웃 여유 확보 (사용률 88% → 44%) |
| CPU 기준 성능 | vCPU당 10% | vCPU당 20% | Unlimited 모드 초과 과금 감소 |

> **CPU 처리량은 근거가 아니다.** t4g 계열은 micro·small·medium 모두 2 vCPU Graviton2로 동일하다. CPU가 병목이면 크기를 올려도 해결되지 않으며 `db.m8g.large`로 계열을 바꿔야 한다.

## 3.6 인메모리 — Redis (ElastiCache)

### 저장 대상

- 사용자에게 추천되었으나 보관함에 등록되지 않은 외출 코스
- 챗봇 의도 카드 입력 정보 (현재 위치, 외출 가능 시간, 선호 장소)
- 영상 분석·코스 추천 진행 상태
- SSE 이벤트 전달용 Pub/Sub 채널

> 자주 읽고 쓰지만 일정 시간이 지나면 필요 없으며, **유실되어도 재요청이나 MySQL 재조회로 복구 가능한 데이터**다.

### 근거

이런 데이터를 MySQL에 저장하면 챗봇 입력 변경마다 UPDATE, 진행 상태 확인마다 SELECT, 만료 정리 DELETE가 발생한다. Redis로 분리해 **DB의 읽기/쓰기 부하를 줄인다.**

### 사이징

**초기: `cache.t4g.small` (1.37 GiB)**

| 항목 | 내용 |
| --- | --- |
| 실제 사용 가능 메모리 | 약 1.03 GiB (`reserved-memory-percent` 기본 25%) |
| 기본 축출 정책 | `volatile-lru` → **모든 Key에 TTL 필수** |
| 네트워크 기준 대역폭 | 0.128 Gbps (버스트 5 Gbps) |

TTL 없는 Key가 쌓이면 메모리 압박 시 축출이 아니라 쓰기 오류가 발생한다.

## 3.7 비동기 처리 — Amazon SQS

### 처리 대상

- 좋아요 영상 목록 추출 후 영상 분석 요청 중계
- 취향·위치 기반 외출 코스 추천 요청 중계
- 알림 중계

### 근거

| 항목 | 내용 |
| --- | --- |
| 운영 부담 | 서버 불필요, AWS가 자동 확장 관리 |
| 내구성 | 메시지 최대 14일 보관, 누락 방지 |
| 비용 | 매달 첫 100만 요청 무료 |
| 중복 처리 방지 | Visibility Timeout으로 처리 중 메시지 은닉 |

### 큐 구성

| 큐 | 역할 |
| --- | --- |
| `keepgo-sync` | YouTube 동기화, 분석 대상 생성 |
| `keepgo-analysis` | 영상별·배치별 분석 |
| `keepgo-notification` | 예약·완료 알림 |
| 각 큐의 DLQ | 반복 실패 작업 격리 |

기본 유형은 **Standard**를 사용한다. 개별 영상 분석은 순서보다 병렬 처리와 재처리가 중요하다.

> 참고: FIFO는 초당 300건(배치 3,000건)이고, 서울 리전은 고처리량 모드에서 2,400 TPS다. 이벤트 버스트 구간의 Job 유입량을 담으려면 Standard가 적합하다.

### 정합성 — Transactional Outbox

```
1. Backend가 Job과 Outbox를 같은 MySQL 트랜잭션으로 저장
2. 사용자에게 jobId와 접수 상태 반환
3. Outbox 발행기가 SQS에 발행
4. Worker가 수신 → 중복·완료 확인 → 외부 API 호출
5. 결과를 MySQL에 저장
6. 저장 성공 후 SQS 메시지 삭제
```

SQS는 **at-least-once**이므로 Worker는 `job_id` 또는 `user_id + video_id + analysis_version`을 멱등성 키로 사용한다.

## 3.8 Worker

### 사이징

**초기 기준: `t3.medium` (2 vCPU / 4 GiB)**

외부 API I/O 중심이라는 가정에 기반한다. 로컬 모델 추론이나 대규모 영상 처리가 추가되면 재검토한다.

### 동시성 상한

```
필요 동시 처리 수 ≈ 초당 Job 유입량 × 평균 Job 처리시간
필요 Worker 수   ≈ 올림(필요 동시 처리 수 ÷ Worker당 동시 처리 수)

Worker당 동시 처리 수
= min(SQS 수신 동시성, HTTP 커넥션 풀 라우트당 상한, 스레드 수)
```

> **Worker를 늘려도 처리량이 늘지 않는 경우가 있다.** 실측에서 Worker 스레드를 4 → 8 → 16으로 늘렸을 때 스레드당 처리량이 457 → 272 → 148로 약 45%씩 감소했다. 인스턴스를 추가하기 전에 **외부 API Rate Limit과 HTTP 클라이언트 커넥션 풀 설정**을 먼저 확인한다.

### 대량 Sync 제어

- 사용자별 중복 Sync 병합
- 마지막 동기화 이후 변경분만 수집
- 이미 분석한 공개 영상의 결과 재사용
- 사용자별 동시 처리량 제한
- 재시도 횟수와 비용 상한 설정

# 4. 최종 아키텍처

```
사용자
 │
 ├─ 정적 웹
 │   └─ CloudFront → S3 (비공개, OAC)
 │
 └─ API / 실시간 연결
     └─ Public ALB
          ├─ /api/*     → ECS Service: keepgo-backend
          │                 └─ Spring Boot Backend
          │                        │ (내부 호출, ALB 미노출)
          │                        ↓
          │                 ECS Service: keepgo-ai-api
          │                   └─ 온라인 AI (챗봇·코스 추천)
          │
          └─ /events/*  → ECS Service: keepgo-sse
                            └─ SSE 서버

Backend
 ├─ RDS MySQL (db.t4g.small) : 사용자·콘텐츠·추천·Job 원장·Outbox
 ├─ ElastiCache Redis        : 캐시·임시 상태·Pub/Sub
 └─ Job + Outbox 저장
              ↓
        Outbox 발행기
              ↓
             SQS
       ┌──────┼──────┐
   sync   analysis  notification
       └──────┼──────┘
              ↓
   ECS Service: keepgo-worker
    ├─ YouTube 동기화
    ├─ 영상 분석 (Gemini)
    ├─ 결과를 RDS에 저장
    └─ 진행률·완료 이벤트를 Redis에 발행
              ↓
         Redis Pub/Sub
              ↓
          SSE 서버 → 사용자

EventBridge Scheduler → 발송 시각 알림 조회 → SQS → 알림 처리
```

## 4.1 ECS 서비스 구성

| Service | Task 구성 | 배치 | 평시 Task | 피크 |
| --- | --- | --- | --- | --- |
| `keepgo-backend` | Spring Boot Backend | `c7i.large` 인스턴스 | 1 | 2 이상, 부하에 따라 확장 |
| `keepgo-ai-api` | 온라인 AI (FastAPI) | Backend와 같은 Capacity Provider | 1 | 동시 처리 요청 수 기준 확장 |
| `keepgo-sse` | SSE 서버 | `t3.medium` 인스턴스 | 1 | 연결 수 기준 확장, 최소 2 검토 |
| `keepgo-worker` | 동기화·분석 Worker | `t3.medium` 인스턴스 | 1 | 큐 적체 기준 확장 |

Task 정의에는 컨테이너별 CPU 단위와 메모리 상한을 명시한다. 한 Service가 호스트 자원을 모두 점유하지 않도록 **예약(reservation)과 상한(limit)을 함께 설정**한다.

## 4.2 가용성 정책

| 구성 | 의미 |
| --- | --- |
| `Task 1 + ASG` | 장애 후 자동 복구. 복구까지 일시 중단 |
| `Task 2 이상 + Multi-AZ` | 일부 장애 중에도 요청 처리 지속 |

KeepGo는 결제·금융 서비스가 아니며 짧은 중단을 허용한다. **비용을 우선해 평시 1대로 시작**하되, 저녁·주말·이벤트 구간에는 Backend와 SSE를 2대 이상 유지한다.

> RDS·Redis·NAT Gateway를 단일 구성으로 유지하는 동안에는 전체 서비스의 단일 장애 지점이 남는다. **V2는 중단 가능성을 수용하면서 확장과 복구를 자동화하는 단계**로 정의한다.

# 5. 네트워크 구조

## 5.1 VPC 구성

AWS 서울 리전, **2개 AZ**에 Public / Private Subnet을 구성한다.

| 위치 | 구성요소 |
| --- | --- |
| Public Subnet (2 AZ) | ALB, NAT Gateway |
| Private Application Subnet (2 AZ) | ECS EC2 (Backend / SSE / Worker) |
| Private Data Subnet (2 AZ) | RDS, ElastiCache |
| VPC 외 관리형 서비스 | SQS, S3, CloudFront, ECR |

```
                    Internet
                       │
        ┌──────────────┴──────────────┐
        │                             │
   CloudFront                    Public ALB
        │                             │
       S3                    ┌────────┴────────┐
   (비공개, OAC)              │                 │
                     Private App Subnet   Private App Subnet
                          (AZ-a)               (AZ-c)
                     ECS EC2 인스턴스      ECS EC2 인스턴스
                             │                 │
                             └────────┬────────┘
                                      │
                          Private Data Subnet (2 AZ)
                              RDS MySQL / Redis

              Private App Subnet → NAT Gateway → 외부 API
                                   (YouTube, Gemini, 지도)
```

- RDS DB Subnet Group은 2개 AZ에 구성하되 **DB 자체는 Single-AZ**로 운영한다
- 외부 API 호출을 위해 NAT Gateway를 통한 송신 경로를 확보한다
- 비용형 초기안에서는 **NAT Gateway 1개**를 사용한다. 해당 경로 장애가 두 AZ의 외부 호출에 영향을 줄 수 있음을 운영 한계로 기록한다

## 5.2 프런트엔드 — CloudFront + S3

정적 React 프런트엔드를 S3와 CloudFront로 분리한다.

| 항목 | 내용 |
| --- | --- |
| S3 | 비공개 유지, CloudFront **OAC**를 통해서만 접근 |
| CloudFront | 정적 자산 캐싱, TLS 종료 |
| 도메인 | 웹용 호스트명 → CloudFront, API용 호스트명 → ALB |

V1에서 EC2의 Nginx가 담당하던 정적 파일 제공 역할이 제거되어, **애플리케이션 EC2는 API 처리에만 집중**한다.

## 5.3 보안 그룹

| 대상 | 허용 소스 | 용도 |
| --- | --- | --- |
| ALB 443 | 인터넷 | HTTPS 진입 |
| ALB 80 | 인터넷 | HTTPS 리다이렉트 |
| Backend 포트 | ALB SG | API 요청 |
| SSE 포트 | ALB SG | 스트리밍 연결 |
| MySQL 3306 | Backend·Worker SG | 영속 데이터 접근 |
| Redis 6379 | 애플리케이션 SG | 캐시·이벤트 통신 |
| AI API 포트 | Backend SG | 온라인 AI 내부 호출 (ALB 미노출) |

- AI·DB·Redis 포트를 **인터넷에 공개하지 않는다**
- 서버 운영 접근은 **SSM Session Manager**를 기본으로 한다

## 5.4 IAM과 Secret

- EC2/Task Role을 Backend·SSE·Worker 역할별로 분리한다
- Worker는 담당 큐의 소비·삭제·Visibility 변경 권한만 가진다
- DB 자격 증명, OAuth Secret, JWT 키, Gemini·지도 API 키는 **Secrets Manager**에서 관리한다
- 이미지와 저장소에 Secret 값을 포함하지 않는다
