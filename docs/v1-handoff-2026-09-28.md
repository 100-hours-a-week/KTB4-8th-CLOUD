## 2. 이번에 반영한 것과 보류한 것

- 실제 FE/BE/AI 저장소와 AWS account를 예시 설정에 반영했다.
- 실제 CI 파일 경로는 확인되지 않아 CONFIGURE 자리표시자로 명시했다.
- Compose의 공통 `/app/bin/healthcheck` 및 서비스별 적용 부분을 주석 처리했다. 이미지 자체 Dockerfile의 HEALTHCHECK를 강제로 끄는 설정은 넣지 않았다.
- `/app/bin/smokecheck`, `/app/bin/queue-metrics`, `/api/health/ready`는 **제안된 계약**이다. 기존 앱에 있다는 사실이 확인되지 않았다.
- 검사 함수를 무조건 성공으로 바꾸지 않았다. runtime의 `app_checks_confirmed=false`일 때 일반 배포·복구 검증을 시작하지 않는다. 계약 확정 후 기존 검사와 연결하거나 구현해야 한다.
- `CD_SETUP_READY=true`가 아니면 후보 수신·권한 있는 PR 정책·배포 workflow는 실행되지 않는다. 수동 dispatch도 준비 확인 전에는 배포를 시작하지 않는다.
- `MONITOR_ENABLED`는 별도 스위치다. 외부 origin/실제 검사 경로/권한을 확인하기 전에는 false로 둔다.
- S3 전달 코드와 S3를 생성하는 IAM/인프라 template은 기존 초안으로 남기고 적용 보류로 표시했다. **S3를 새로 만들어야 하는 작업 목록으로 해석하지 않는다.**

현재 Compose는 준비용 소스다. health 주석만 바꿨다고 기존 EC2에 바로 적용할 수 있는 것은 아니다. Worker 이미지가 없고, awslogs log group 존재 여부와 실제 호스트 설정도 미확인이다. `docker compose up`으로 현재 스택을 덮어쓰지 않는다.

## 4. EC2 담당자에게 보낼 요청문

아래 내용을 복사해 전달할 수 있다. 이 문서 작성 과정에서 팀원에게 메시지를 보내지는 않았다.

```text
중앙 CD와 장애 알람을 기존 EC2에 연결하려고 합니다.
EC2를 새로 만들거나 지금 실행 중인 컨테이너를 내리려는 작업은 아닙니다.

1. EC2 인스턴스 ID / OS / SSM Online 여부 / instance role 이름
2. 현재 Compose 파일의 경로와 project name, 작업 디렉터리
3. 실행 중인 서비스 이름과 이미지 URI:tag
4. EC2에 Cloud repo checkout이 있는지, 있다면 경로와 읽기 인증 방식(키 내용 제외)
5. 운영 도메인, TLS 인증서 mount 경로와 갱신 담당
6. CloudWatch log group / alarm / SNS 설정 유무
7. 기존 배포 방법과 직전 버전으로 돌아가는 방법

비밀번호, 키, 전체 .env, Secret 내용은 제외해 주세요.
```

서비스/이미지 목록은 해당 호스트에서 다음 읽기 명령으로 확인할 수 있다. 로그/출력에 업무상 민감한 이름이 있으면 확인 후 공유한다.

```sh
docker compose ls
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
# 실제 Compose 디렉터리에서 실행
docker compose config --services
docker compose config --images
```

환경변수가 펼쳐질 수 있는 전체 `docker compose config`, `docker inspect`, `env`, .env 출력은 요청하지 않는다.

## 5. S3 없이 진행할 후속 작업

현재 `scripts/ssm-deploy.py`는 S3 업로드/다운로드를 사용하고 `infrastructure/cd-access.yaml`은 bucket을 생성한다. 이 두 파일과 배포 workflow의 DEPLOY_BUCKET 요구는 현 환경에 맞지 않는다.

현재 제안은 **SSM으로 기존 EC2에 지시하고, 읽기 인증이 된 Cloud checkout에서 고정된 commit을 별도 release 디렉터리로 확보하는 방식**이다. 운영 중인 checkout을 main으로 강제 변경하거나 git reset으로 팀원의 파일을 덮어쓰지 않는다. 실제 clone 경로·인증·권한을 확인한 뒤 다음을 함께 수정한다.

1. S3 코드 전달을 고정 commit checkout/archive 방식으로 교체.
2. workflow의 DEPLOY_BUCKET 입력과 IAM의 bucket/resource/권한 제거.
3. 기존 runtime·운영 이미지·state와 새 release 스냅샷 연결.
4. 다운로드/인증 실패는 서비스 중단 전에 실패하도록 검증.

이 대체 전달 방식은 아직 구현하지 않았다. 지금 S3 버킷 정보를 추가로 줄 필요도 없다.

## 6. 앞으로의 순서

1. 현재 소스와 문서를 준비용으로 검토/푸시. 자세한 분류는 [파일 역할·푸시 지침](v1-files-and-push-guide.md).
2. EC2 담당자 인계와 앱 CI 경로 확인. 기존 EC2/리소스 재사용 여부 결정.
3. S3 없는 전달 코드·최소 IAM으로 변경하고 GitHub 설정 연결.
4. Worker 게시 준비와 앱 health/검증 계약 확정. 기존 구현이 있으면 거기에 맞춤.
5. 기존 로그/알람을 조회한 뒤 빠진 CloudWatch/SNS 구성만 설치, 수신 확인.
6. 실제 SHA/run ID로 Manifest 작성, 최초 CD 관리 상태 전환 절차 검토. 기존 서비스는 상태 확인 없이 중지하지 않음.
7. 정상 배포, Backend/Worker 독립 교체, 실패 롤백, job 회수, 알람 시험.
8. 검사 주석을 실제 구현에 맞춰 복구하고 app_checks_confirmed, GitHub 준비/자동화 스위치를 단계적으로 활성화.

현재 CloudWatch·SNS·GitHub 설정을 직접 조회하거나 변경하지 않았다. 현재 계정에 없는 Worker ECR도 생성하지 않았다.
