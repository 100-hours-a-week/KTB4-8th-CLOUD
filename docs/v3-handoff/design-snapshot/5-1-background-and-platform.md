## 1. 문서 개요

KeepGo V3에서 해결해야 하는 운영 문제를 정의하고, 이를 충족하기 위한 운영 플랫폼을 선정했습니다.

서비스와 개발 조직의 확대를 가정하여 팀별 독립 배포, 운영 정책 표준화, 권한 분리 및 워크로드별 확장 요구사항을 도출했습니다. 단순 MAU, 트래픽 증가만으로 Kubernetes 도입을 결정하지 않았습니다.

배경 가정을 정하고 플랫폼별 기능뿐 아니라 운영 책임, 기존 AWS 환경과의 연계, 장애 대응 및 비용을 비교하여 KeepGo에 적학한 방안을 결정합니다.

### 이 문서에서 결정할 사항

- 서비스·조직 성장에 대한 가정과 운영 요구사항
- ECS 유지와 Kubernetes 도입의 판단 기준
- 플랫폼별 관리 범위와 운영 부담
- 최종 플랫폼 및 선택에 따른 이점과 제약

### 2.2 운영 요구사항

```hcl
기능별 담당 팀이 공통 인프라를 사용하는 환경에서는 트래픽 처리 능력뿐 아니라

```

| 운영 요구사항 | 필요한 이유 | 확인 사항 |
| --- | --- | --- |
| 팀별 배포 대상 관리 | 여러 팀의 배포 일정과 담당 범위의 스케일이 달라짐 | 담당 워크로드별  배포·롤백과 영향 범위 관리 |
| 접근 권한 분리 | 답당 업무에 따라 조회·변경 권한이 달라짐 | 팀별 최소 권한 적용과 변경 이력 추적 |
| 자원 사용 범위 관리 | 공통 자원을 사용하는 팀 사이에 자원 경합이 발생할 수 있음 | 팀별 자원 할당과 사용량 제한 |
| 워크로드별 확장·배치 | HTTP 요청, SSE 연결, 비동기 작업의 부하 특정이 다름 | 부하 지표별 확장과 배치 정책 적용 |
| 운영 정책 표준화 | 팀마다 설정이 달라지면 누락과 관리 부담이 증가함 | 공통 배포 설정·보안 정책의 재사용과 적용 |
| 장애 대응 책임 구분 | 공통 인프라 장애와 개별 워크로드 장애의 담당이 다름 | 팀별 상태 확인과 플랫폼 운영팀의 통합 관측 |

→ 위의 요구사항들은 물론 기존 ECS 환경과 AWS 서비스들을 이용하면 충분히 운영이 가능합니다. 하지만 Kubernetes를 도입하는 방안을 비교했을 때의 이점을 평가하겠습니다.

### 2.3 Kubernetes 도입 조건 정의

```hcl
KeepGo는 서비스 규모와 개발 조직이 확대되면서 여러 팀의 워크로드를 공통 인프라에서 운영하는 상황을 가정합니다. 
이에 따라 단순히 사용자 수나 애플리케이션 수의 증가가 아니라, 팀별 운영 범위와 공통 정책을 일관되게 관리할 필요가 있습니다.
```

1. **팀별 자원/권한 관리**

담당 팀별 변경 권한과 자원 사용 범위를 정의합니다.

→ 여러 팀이 공통 클러스터를 사용하면서 팀 단위의 권한과 자원 할당 정책을 반복적으로 적용해야 합니다.

2. **워크로드 배치 제어** 

사용자 요청 처리 용량을 확보하고, 분석 작업과의 자원 경합을 줄입니다.

→ 워크로드별 실행 노드를 구분하고, 장애 대응을 위한 분산 배치 정책을 세밀하게 관리해야 합니다.

3. **워크로드별 확장**

HTTP 요청, SSE 연결, 분석 큐 등 서로 다른 부하를 기준으로 확장합니다.

→ 서로 다른 확장 정책을 공통된 운영 체계 안에서 관리하고, 외부 API 호출 제한까지 고려해야 합니다.

4. **배포 설정 관리와 GitOps**

배포 설정의 변경 이력을 관리하고, 검토한 설정과 실제 운영 상태를 일치시킵니다.

→ 여러 팀과 환경의 설정 변경이 늘어나 수동 변경 및 설정 불일치를 지속적으로 통제해야  합니다.

5. **운영 표준화**

자원 설정, 상태 확인, 배포 및 관측 기준을 공통으로 적용합니다.

→ 팀이 늘어날 때마다 개별 설정을 만드는 방식보다 공통 템플릿과 정책으로 관리하는 방식이 필요합니다.

### 2.4 기존 ECS 비교

- 같은 컨테이너 오케스트레이션인데 왜 하필 k8s를 사용해야 하나? 라는 생각을 해결해보겠습니다.

#### ESC와 k8s

ECS와 Kubernetes는 모두 컨테이너 오케스트레이션 플랫폼입니다.

즉, 컨테이너를 실행하고, 배포하고, 확장하고, 장애가 발생하면 복구하는 데 있어서 공통의 목적을 가지고 있습니다.

|  | AWS ECS | Kubernetes |
| --- | --- | --- |
| 컨테이너 관리 범위 | Cluster | Cluster |
| 컨테이너 실행 단위 | Task | Pod |
| 실행 단위 설정 | Task Definition | Pod Specification |
| 원하는 실행 개수 유지 | ECS Service | Deployment +
ReplicaSet |
| 실행 위치 결정 | ECS Scheduler | kube-scheduler |
| 자동 확장 | ECS Service Auto Scaling | HPA |
| 서버 자동 확장 | Capacity Provider /
ASG | Cluster Autoscaler /
karpenter |
1. **첫번째 차이 - 팀별 운영 정책을 적용하는 방식**
    - ECS에서는 IAM 정책으로 리소스에 대한 제한 접근 권한을 제어하고, Task의 CPU·메모리 설정과 클러스터·용량 구성을 통해 자원 사용을 관리합니다.
    - Kubernetes에서는 Namespace를 관리 범위로 삼아 RBAC, ResourceQuota, LimitRange 등을 연결할 수 있습니다.
    
    | 운영 요구 | ECS에서의 방식 | k8s에서의 방식 |
    | --- | --- | --- |
    | 담당 팀의 리소스만 변경 | IAM의 리소스·태그 조건 등을 활용하여 권한 구성 | Namespace 범위의 Role·RoleBinding 구성 |
    | 개별 실행 단위의 자원 설정 | Task Definition에서 CPU·메모리 설정 | 컨테이너의 requests·limits 설정 |
    | 팀 전체의 지원 사용 범위 관리 | 용량 분리 또는 배포 검증 등 별도 관리 방식 설계 | Namespace별 ResourceQuota 적용 |
    | 팀별 기본 자원 설정 적용 | Task Definition 템플릿과 배포 검증으로 관리 | LimitRange와 배포 템플릿으로 관리 |
    
    → 즉, Kubernetes가 ECS보다 권한 관리나 자원 제한을 더 잘한다는 게 아닌, 여러 팀의 운영 환경을 하나의 클러스터 안에서 표준화하고 반복적으로 제공하기 쉽다는 뜻입니다.
    
    ```hcl
    KeepGo V3에서는 이러한 환경 제공이 반복된다고 가정하므로, 
    팀별 관리 범위와 정책을 Kubernetes 리소스로 함께 구성하는 방법을 채택하고자 합니다.
    ```
    
2. **두번째 차이 - 배치 규칙을 표현하는 범위**
    - Kubernetes에서는 노드의 조건뿐 아니라 Pod 사이의 관계, 배치 조건의 강제 여부 및 분산 정도를 조합하여 정책을 정의할 수 있습니다.
    
    | V3에서 가정한 배치 요구 | Kubernetes 적용 방식 |
    | --- | --- |
    | Worker 전용 노드에 일반 워크로드의 배치를 제한 | Taint·Toleration과 노드 선택 조건 조합 |
    | 여러 AZ 사이의 Pod 수 편차를 관리 | Topology Spread Constraints |
    | 필수 배치 조건과 선호 조건을 구분 | Affinity와 required·preferred 조건 |
    
    ```hcl
    KeepGo V3에서는 팀과 워크로드가 늘어나면서 이런 배치 규칙을 조합하고 반복적으로 변경해야 한다고 가정합니다. 
    이에 따라 워크로드별 배치 의도를 선언적으로 표현하고 공통 템플릿으로 관리할 수 있는 Kubernetes의 기능을 활용합니다.
    ```
    
3. **세번째 차이 - 공통 API를 중심으로 운영 도구를 연결하는 방식**
    - ECS도 IaC와 배포 파이프라인을 활용하여 설정을 코드로 관리하고 운영 절차를 표준화할 수 있습니다.
    - 하지만, Kubernetes에서는 애플리케이션 배포, 접근 권한, 자원 할당 및 배치 정책을 Kubernetes API가 이해하는 리소스로 표현할 수 있습니다. 여기에 Helm과 Argo CD 등의 도구를 연결하여 공통 템플릿과 Git 기반 배포 관리 체계를 구성할 수 있습니다.
    
    ```hcl
    KeepGo V3에서는 다음과 같은 운영 방식을 목표로 합니다.
    
    이를 통해 신규 팀마다 별도의 운영 방식을 만드는 부담을 줄이고, 공통 정책의 변경과 적용 여부를 일관되게 관리하고자 합니다
    
    1. Argo CD가 Git의 Kubernetes 설정과 클러스터 상태를 비교하고, 정해진 동기화 정책에 따라 반영합니다.
    2. Git에서 변경 내용을 검토하고 이력을 관리합니다.
    3. 각 팀은 허용된 범위에서 이미지 버전과 워크로드별 설정을 변경합니다.
    4. 플랫폼 운영팀이 공통 배포 템플릿과 기본 정책을 관리합니다.
    ```

## 3. Kubernetes 도구 비교 및 선택

- 3가지의 방법을 고려하려고 합니다
    - EC2 + kubeadm : AWS EC2에 Kubernetes 클러스터를 직접 구축하고 운영합니다.
    - Amazon EKS : AWS가 제공하는 관리형 Kubernetes 서비스를 이용합니다.
    - Google GKE : Google Cloud가 제공하는 관리형 Kubernetes 서비스를 이용합니다.

### 3.1 후보군 비교

1. **EC2 + kubeadm - 제어 범위는 넓지만 직접 운영할 영역이 많습니다.**
    - 기존 AWS 환경을 유지하면서 Control Plane과 노드 구성을 직접 제어할 수 있습니다.
    - 하지만, API Server와 etcd의 고가용성, 인증서 관리, 백업·복구 및 업그레이드 절차까지 신경써야할 것들이 많습니다.
    
    → 관리형 클러스터의 요금이 추가로 발생하지 않더라도 Control Plane 관리와 학습/운영 비용의 전체 운영 비용이 더 낮다고는 생각하지 않습니다.
    
2. **Amazon EKS - 기존 AWS 환경을 유지하면서 Control Plane 운영 부담 감소**
    - EKS를 사용하면 Control Plane 운영을 AWS에게 넘기고, 워크로드의 배포/권한/자원/관측 정책에 집중할 수 있습니다.
    - 기존 AWS 환경에 있는 RDS, SQS, S3, ECR 등을 유지하는 방향으로 전환 범위를 선택할 수 있습니다.
3. **Google GKE - 우수한 관리형 기능을 제공하지만 플랫폼 이전과 학습 부담 발생**
    - 관리형 Control Plane과 노드 자동 업그레이즈/복구 기능을 제공하여 kubernetes 운영 부담을 줄일 수 있습니다.
    - KeepGo의 기존 AWS 환경을 Google Cloud로 이전하려면 네트워크, 접근 권한, 배포 파이프라인을 재구성하고 데이터와 연계 서비스의 이전을 검증해야 합니다.
    
    → Kubernetes와 함께 Google Cloud의 IAM, VPC, 관측 도구 및 과금 체계를 새롭게 학습해야하고 플랫폼 이전 비용과 추가 학습 부담이 발생합니다.
    

### 3.2 최종 선택 - Amazon EKS

```hcl
KeepGo V3에서는 Kubernetes 운영 플랫폼으로 Amazon EKS를 선택하려고 합니다. 
기존 AWS의 데이터·메시징 서비스를 유지하면서 Control Plane 운영을 AWS에 위임하고, 
플랫폼 운영팀은 팀별 배포 환경과 권한/자원 정책의 표준화에 집중하려고 합니다.

이에 따라 기존 환경 활용과 운영 책임의 균형을 고려하여 EKS를 선정했습니다.

EC2와 Kubeadm을 이용한 직접 구축은 Control Plane까지 운영해야 하는 부담이 있으며, 
GKE는 기존 환경의 이전·연계와 새로운 클라우드 학습이 필요합니다.
```
